# AI Memory Hub 后台规范

- 状态：执行规范
- 适用范围：Dashboard / Console 前端、Dashboard API、任务与 Agent 协作展示
- 目标：让人先看懂系统正在发生什么，再决定是否介入；让后台加载只取当前页面需要的数据。

## 1. 产品定位

后台是“团队工作台”，不是内部数据转储器。首页回答“团队现在在推进什么”，任务页回答“我现在应该处理什么”，其他页面分别承担记忆、消息、工作流、调度、工具和健康检查职责。

所有页面必须遵循：

1. 先展示结论和可行动状态，再展示技术字段。
2. 条目默认使用列表、队列、时间线或看板等适合内容的布局，不把所有内容做成大卡片。
3. 点击条目打开弹窗或详情页；不在当前页面末尾追加不明显的详情。
4. 技术 ID、原始 JSON、错误堆栈等放入“技术详情”或折叠区域。
5. 数据为空、加载中、加载失败和无权限必须有明确状态，不允许留白让用户猜测。

## 2. 信息架构

### 2.1 概览

概览是行动入口，不是全量报表。推荐顺序：

1. 团队工作台标题和实时状态
2. 当前活跃 Agent
3. 需要关注的任务
4. 最近任务
5. 协作消息

概览首屏只加载活动 Agent、需要关注的任务、最近任务和最近协作消息。健康、记忆、工具等深层数据按页面或明确操作加载。

### 2.2 任务

任务页是“工作队列”，使用横向条目列表，不使用内容卡片墙作为默认布局。每一行至少展示：标题、状态、优先级、项目、负责人、更新时间和可执行操作。

页面顺序：

1. 任务队列标题、结果数量、新增任务
2. 状态统计：待处理、已认领、进行中、待验证、已完成
3. 筛选工具栏：搜索、状态、项目、优先级、清除筛选
4. 任务列表

任务条目点击后打开完整详情弹窗。条目上的快捷操作可以保留，但弹窗必须提供同等或更完整的操作入口。

### 2.3 其他页面

- 共享记忆：记录列表 + 内容详情；原文编辑使用弹窗。
- Radio：消息流 + 消息详情；消息按时间和发送关系展示。
- 工作流：阶段带 + 工作流列表 + 节点/动作详情。
- 调度：控制区 + 运行队列 + 运行详情。
- 工具：工具清单 + 健康状态 + 配置弹窗。
- 备份：备份集列表 + 文件/恢复详情。
- 健康：问题摘要 + 修复计划 + 原始报告折叠区。
- 搜索：结果列表 + 类型、来源、时间等筛选；详情弹窗或右侧详情。

## 3. 任务状态与人工审核

### 3.1 人类可读状态

内部状态必须在 UI 中转换为自然语言：

| 内部值 | 中文展示 |
| --- | --- |
| `open` | 待处理 |
| `claimed` | 已认领 |
| `in_progress` | 进行中 |
| `needs_verification` / `waiting_review` | 待验证 |
| `blocked` | 已阻塞 |
| `done` / `completed` | 已完成 |
| `cancelled` | 已取消 |
| `failed` | 失败 |

原始状态值仅在技术详情中展示。

### 3.2 人工审核边界

默认不要求人工审核普通 Agent 之间的任务流转，也不要求因为“别人给 Agent 派了任务”而暂停用户。只有高风险或不可逆操作保留人工审核，例如：

- 安装依赖或修改系统配置
- 远程 Git push 或外部发布
- 删除、purge、物理清理数据
- 破坏性恢复、批量覆盖
- 明确声明 `reviewRequired` 的质量门禁

审核入口必须说明：风险是什么、会改变什么、谁发起、谁执行、如何撤销。审核不是所有页面的默认视觉中心。

### 3.3 Agent 与工具边界

Antigravity 是独立 Agent/工具，不是 Gemini 的升级或替代。任务可以手动修改目标工具为 Antigravity，但不应通过修改 Agent 定义来伪装工具替换。Gemini、Antigravity、Codex 等运行器必须在工具注册表中保持独立身份、能力和配置。

## 4. 筛选与交互规范

### 4.1 选择规则

- 搜索文本：单值输入，placeholder 放在输入框内，不单独占一行显示“搜索文本”。
- 状态：多选。
- 项目：多选，选项多时使用可搜索弹出面板。
- 优先级：多选。
- 清除筛选：清空搜索、状态、项目和优先级，恢复全部条目。
- 筛选弹出面板：点击外部、失去焦点或按 `Esc` 自动关闭。
- 弹出面板只能有一个滚动容器，不能出现嵌套双滚动条。

筛选栏在桌面端保持一行；宽度不足时允许工具栏横向滚动或收缩，但不能让搜索输入被单独挤成一行。移动端才切换为纵向布局。

### 4.2 弹窗详情

弹窗默认展示完整工作信息，而不是只复制条目摘要。任务弹窗至少包含：

- 标题、状态、优先级
- 描述
- 项目、负责人、创建人
- 创建时间、更新时间、任务 ID
- 交接说明
- 交付状态、执行次数、重试上限、进度、审核状态
- 最近错误
- 最近活动记录
- 当前状态可执行的全部操作

原始 JSON、长错误堆栈和内部上下文放入可折叠的技术详情区。弹窗必须遵守视口约束：最大高度不超过视口，内容区独立滚动，底部操作区始终可见，小屏也不能上下截断。

### 4.3 操作反馈

所有写操作必须提供加载中、成功、失败反馈；操作完成后刷新当前页面数据或局部更新条目。按钮文案必须表达结果，例如“请求验证”“验证通过并完成”，避免只写“提交”“执行”。

## 4.4 视觉层级与信息去重（新增）

后台页面必须控制视觉块的数量，避免把每个指标、筛选项和状态都包装成独立卡片。默认采用“页面头部 → 核心控制 → 筛选 → 主列表 → 弹窗详情”的单向层级。

- 全局页面头部是唯一主标题；子页面不得重复展示同一标题、摘要和结果数量。
- 同一组统计数据只能有一个主要呈现位置。状态 Tab 已经展示数量时，不再额外重复显示同样的统计卡片。
- 统计优先使用一行摘要或轻量文本，只有需要对比或快速决策时才使用卡片。
- 状态筛选优先使用轻量 Tab/导航，不使用大面积白色块堆叠。
- 主页面保持稳定，执行图、节点详情、长文本和技术信息进入弹窗或折叠详情。
- 列表条目整体可点击时，仍需保留明确的按钮入口；按钮不能成为唯一入口。
- 所有按钮必须有真实行为；未实现的创建、启动、暂停、重试等动作不得伪装成可用功能。
- 任何背景色、边框或状态色都不能牺牲文字可读性；必须检查文字与背景的对比度。

工作流页的参考结构为：全局页面头部 → 状态 Tab（包含状态数量）→ 搜索/项目筛选 → 工作流队列 → 执行图弹窗。工作流总数、活跃、待审核和阻塞不再作为另一组重复卡片显示。

## 5. 数据加载与 API 规范

### 5.1 按页面懒加载

禁止所有页面初始化都请求全量 `/api/dashboard`。页面必须优先请求自己的数据接口：

| 页面 | 首选接口 |
| --- | --- |
| 概览 | `/api/dashboard/overview` |
| 任务 | `/api/tasks` |
| 记忆 | `/api/memory` |
| Radio | `/api/radio` |
| 工作流 | `/api/workflows` |
| 调度 | `/api/dispatch` |
| 工具 | `/api/tools` |
| 备份 | `/api/backups` |
| 项目 | `/api/projects` |
| 分析 | `/api/metrics` |
| 设置 | `/api/settings` |
| 健康 | `/api/health` |

全量 `/api/dashboard` 仅用于兼容、调试或明确需要全局快照的场景。

### 5.2 性能目标

- 概览轻量首屏响应体目标：小于 200KB。
- 普通页面首屏只请求当前页面数据，不得因为无关模块计算阻塞。
- 交互页面首次可见内容目标：1 秒内显示骨架或已有数据。
- API 必须避免把 notes、原始错误、完整历史和大字段重复放入列表响应。
- 列表与详情分离：列表返回摘要，点击后再请求或展示完整详情。
- 所有页面必须有加载骨架或明确加载提示，不以空白代替加载状态。

### 5.3 实时更新

实时连接只推送当前页面需要的变化或轻量摘要。收到更新后优先局部更新；不能每次文件变化都重新计算并发送全量快照给所有页面。

## 6. 文案与数据展示

- 面向人类的主界面使用中文自然语言；英文模式保持等价语义。
- 不直接展示 `sessionId`、`threadKey`、`deliveryState` 等内部字段名。
- 技术字段使用中文标签，例如“会话 / 消息 ID”“交付状态”“执行次数”。
- 时间统一使用用户本地时间，并尽量展示“刚刚、5 分钟前”等相对时间；详情中可同时显示完整时间。
- 错误信息先给出可理解的摘要，再提供原始错误展开查看。
- 空状态必须说明下一步，例如“暂无需要介入的任务”“创建或认领任务后，近期进展会显示在这里”。

## 7. 验收清单

### 视觉与交互

- [ ] 页面布局按内容类型选择列表、队列、时间线、看板或卡片。
- [ ] 条目点击有明确反馈，并打开弹窗/详情。
- [ ] 弹窗信息不少于条目，并提供完整操作。
- [ ] 弹窗在小屏和短窗口中完整可用，底部操作不被截断。
- [ ] 筛选多选规则明确，外部点击和 `Esc` 可关闭面板。
- [ ] 项目选项多时只有一个滚动容器。
- [ ] 空、错、加载三种状态均可理解。

### 性能

- [ ] 页面未无条件请求全量 `/api/dashboard`。
- [ ] 首屏请求只包含当前页面数据。
- [ ] 列表不携带不必要的大型历史字段。
- [ ] 记录真实响应时间、响应体大小和首次可见时间。
- [ ] 修改后执行前端构建并重启实际提供静态资源的后台进程验证。

### 安全与治理

- [ ] 普通 Agent 流转不强制人工审核。
- [ ] 高风险、不可逆和明确质量门禁操作保留审核。
- [ ] Antigravity 与 Gemini 在配置和展示上保持独立。
- [ ] 删除、purge、push、安装和系统配置变更有明确确认和审计记录。

## 8. 实施优先级

1. P0：按页面拆分加载，修复任务页和弹窗视口问题。
2. P0：任务页列表化、筛选规则、弹窗完整信息和操作一致性。
3. P1：Radio、工作流、调度、健康页按内容类型重排。
4. P1：列表摘要与详情接口分离，减少大字段传输。
5. P2：实时更新按页面订阅，补充相对时间、错误摘要和局部更新。

后续任何后台页面改动都必须以本规范为验收基准；若需要偏离，必须在对应页面说明原因和替代交互。
